# Y1: encode — меньше перезагрузок таблиц

## Документы конкурса
Условия конкурса: [`docs/challenge/README.md`](../../docs/challenge/README.md) (обзор, ссылки на сайт), [`SPEC.md`](../../docs/challenge/SPEC.md) (что считать), [`RULES.md`](../../docs/challenge/RULES.md) (замер и запреты), [`LEADERBOARD.md`](../../docs/challenge/LEADERBOARD.md) (соперники). Прочитай их до первой гипотезы.

## Факты
- Замер фаз encode (P3): перезагрузка таблиц группы стоит **2.25 мс**. Каждый CTA (256 строк одного операнда) на каждую из 15 групп по 8 простых грузит 8 КБ твиддлов + 7 КБ B-фрагментов: 225 КБ на CTA, 14.7 ГБ из L2 на батч.
- Сетка encode256 — (n/256, 2, B): a и b одной пары — разные CTA с одинаковыми таблицами.
- 128 регистров на поток, 2 CTA/SM; A-фрагменты `a[2][7][4]` (56 регистров) живут всё ядро. Shared ≈ 39 КБ на CTA.
- TMA multicast по кластеру дал верный ответ, но 784 мс — путь cp.async.bulk на этой машине не годится.

## Задача
Оценить и, если оценка ≥ 0.4 мс, сделать один вариант:
1. Один CTA обрабатывает a и b одной пары внутри каждой группы, таблицы грузятся один раз на оба операнда. Где держать A-фрагменты второго операнда (регистров нет): в shared (сколько КБ?) или перечитывать из L2 каждую группу (сколько ГБ?)?
2. Больше строк на CTA тем же числом потоков (A-фрагменты частично в shared).
3. Свой вариант.

Для каждого: трафик L2, shared на CTA, занятость (CTA/SM), барьеры, ожидаемые мс.
Сравнение — по строке `gpu31 stages` с master `31b7eb8` (encode 14.01).
