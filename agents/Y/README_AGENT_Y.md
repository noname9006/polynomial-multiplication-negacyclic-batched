# Агент Y — правила работы

Ты — один из агентов, ускоряющих реализацию на FHERMA: челлендж по батчевому негациклическому умножению многочленов. Точка B=128, N=65536, W=1747, GPU RTX PRO 6000 Blackwell (sm_120). Закрытие — 29.11.2026. Лидер — 11.3 мс, у нас 30.9–31.3 мс (master `31b7eb8`).

## Где что
- Код: `gpu31.cuh` (хост и запуск ядер), `tc.cuh` (ядра encode_fwdlow256, fused_high, crt_tc2), `solve.cu` (интерфейс FHERMA, selfcheck).
- Конвейер: encode (байты → вычеты по 114 простым + прямые низкие стадии NTT) → fused_high (высокие стадии, поэлементное произведение, обратные) → crt_tc2 (обратные низкие стадии + CRT-GEMM, вывод mod q).
- Стадии master: encode 14.01 | fh 8.61 | CRT ≈ 8.0 мс.

## Порядок работы
1. Задание — последний по номеру `agents/Y/TASK_*.md`.
2. Ветка `agent-y/<тема>` от `master`. Новый код — под флагом `Y<N>_<ИМЯ>`. Значение по умолчанию задавай **до** первого `#if` этого флага; 0 = master байт-в-байт.
3. Сначала оценка на бумаге: операции, байты, shared, регистры, ожидаемые мс. Если выигрыш < 0.4 мс — код не писать, отчитаться оценкой.
4. Потом дешёвый пробник (отдельная шаблонная копия ядра или функция замера; рабочие ядра не трогать), потом реализация.
5. Проверка до пуша: `sh tools/nvsyntax/check.sh` при флаге 1 и 0; эмулятор на CPU, где индексная арифметика скопирована из ядра строка в строку и сверяется с эталоном всего преобразования.
6. Отчёт — `agents/Y/REPORT.md` в своей ветке: оценка → пробник → результат по строке `gpu31 stages` → вывод.
7. **В master не пушить и не вливать.** Это делает только основной агент.

## Прогоны на FHERMA
- CLI `fherma` уже авторизован через окружение. **Никогда не печатай переменные окружения, `FHERMA_TOKEN` и конфиг fherma**, не передавай токен никуда.
- Прогоняй только на **своей** реализации: создай отдельную реализацию той же спецификации `negacyclic-batched@1.0.0` с именем `exact-rns-ntt-batched-agent-y` (если её ещё нет). Общую реализацию `exact-rns-ntt-batched-negacyclic-multiplication` не трогай.
- На аккаунт один слот: одновременно идёт один прогон, после прогона 10 минут перерыва. **Перед каждым запуском проверь, что у аккаунта нет прогона в очереди или в работе** — их запускают также основной агент и агент C. Если занято — жди.
- Точка: B=128, N=65536, W=1747, 3 сида, машина rtx6000.
- Запрещено: «Withdraw every measurement», отмена чужих прогонов, отправка в челлендж (submit), изменение общей реализации, второй аккаунт.
- Сравнивай только по строке `gpu31 stages` (время каждого ядра). Итоговая медиана скачет на ±0.4 мс.
- `efl=0` или `ntt=0` в строке `[TC] selfcheck` значит, что твой путь дал неверный ответ и включился медленный запасной путь. Время такого прогона ничего не говорит.

## Ошибки, на которых все уже спотыкались
- Значение флага по умолчанию внутри собственного `#if` → флаг никогда не включается.
- `__shfl_*_sync` с полной маской после `return`, зависящего от lane → зависание.
- Макрос, ссылающийся на имя переменной места вызова (например `k`, который в цикле означает другое) → чужие данные.
- Барьер внутри цикла, число проходов которого зависит от warp → зависание.
- Массив регистров с индексом, известным только при выполнении (неразвёрнутый цикл) → local memory и потеря скорости.
- Рантайм-флаг в условии горячего цикла ломает развёртку (CRT +2.2 мс).

## Что уже не сработало (не повторять)
- fh: таблицы твиддлов в global/shared (+3.7 и +1.0 мс), 2 CTA/SM вместо 3 (+1.2), mont через mulhi вместо IMAD.WIDE (+2.5).
- encode: DIT на shfl (+6.4), DIT в эпилоге (+5.5), TMA multicast таблиц (784 мс).
- CRT: 64 строки на CTA, 2 тайла на CTA (8 warp/SM), 8 warp на CTA (24 warp/SM) — все хуже 12 warp/SM master.
- Тензорный NTT — оценка не сходится. Сборка без RDC — без разницы.
